2.1 Cloud data concepts Study guide reference: Maps to Chapter 3, Cloud Data Security (Cloud Data Lifecycle section). Data dispersion and data flows also appear in Chapter 3.

The data lifecycle, dispersion, and flows

Data is intangible, constantly created, moved, and eventually discarded, which makes it harder to secure than a physical asset. The practical answer is to model the stages data passes through and attach the right controls to each stage, rather than trying to track every individual data element in the organisation.

The six lifecycle phases

The cloud secure data lifecycle has six phases: create, store, use, share, archive, destroy. The exam expects you to know the sequence, and more importantly, which controls belong to which phase.

  • Create, when data first enters a system or existing data is modified. The critical control here is data classification, because everything downstream depends on knowing how sensitive the data is.
  • Store, committing data to a repository. Storage often happens at the same moment as creation, for example a document uploaded the instant it is written. Encryption in transit matters here, since data frequently crosses public networks on its way to cloud storage.
  • Use, accessing, viewing, and processing data. This is typically the longest phase of the lifecycle, and its controls are correspondingly extensive, covering access management, monitoring, and protection of data in use.
  • Share, granting access to other users or entities. Access controls are the backbone here. Proactive controls include access granting procedures and role based authorisation. Reactive controls include Information Rights Management, Data Loss Prevention, and access reviews, which detect and can sometimes block unauthorised sharing.
  • Archive, long term storage for data no longer in active use, often driven by mandatory retention in sectors such as healthcare and finance. Archive controls resemble storage controls, with one extra complication: encryption keys age. If a key must be retired, archived data may need to be decrypted and re-encrypted under the new key, which is labour intensive at scale.
  • Destroy, secure disposal once data has no value and no retention obligation. Methods range from weak, such as deleting filesystem pointers, to strong, such as overwriting or cryptographic erase. The method should be proportionate to the value of the data: public information does not need extraordinary destruction, while personal data does.
Example

A bank generates a customer statement (create), writes it to cloud object storage over an encrypted connection (store), serves it to the customer through online banking for months (use), sends a copy to the customer's accountant on request (share), moves it to low cost archival storage to satisfy a seven year retention rule (archive), and cryptographically erases it when the retention period ends (destroy). Each handover point has its own control set.

Watch this in the exam

Scenario questions often name an activity and ask which phase it belongs to, or name a control and ask where it applies. Classification belongs to create. IRM and DLP are share phase controls. Key ageing is an archive phase problem. If a question describes the longest running phase, it means use.

Data dispersion

Data dispersion breaks data into smaller chunks and distributes them across multiple physical storage devices, much like striping in RAID. Cloud implementations add erasure coding, which works like parity in RAID: if some segments are lost, the remaining segments plus the parity information can reconstruct the missing data.

The security effect cuts both ways. Availability improves, because the failure of one physical device does not lose the data, and a single compromised device does not hold a complete usable copy. The risk is jurisdictional: segments dispersed across regions can land in countries with unexpected legal requirements. Most providers now offer geographic restriction features so customers get the resilience benefit without the regulatory exposure.

Example

A maritime company's vessel records are dispersed across a provider's storage estate. A failed disk in one data centre loses nothing, because the segments elsewhere reconstruct the data. But without geographic restrictions, some segments could end up stored outside the UK and EU, dragging the data under laws the company never planned for. Configuring region restrictions keeps the resilience and drops the legal surprise.

Data flows

Understanding where data travels is a design responsibility. The three states to track are data in transit, moving across networks between users, services, and clouds; data at rest, held in storage; and data in use, being actively processed. Each state has its own protection profile: encryption in transit, encryption at rest with access controls, and emerging protections such as confidential computing for data in use. Mapping data flows also surfaces compliance obligations, since a flow that crosses a border can trigger residency requirements under regimes such as GDPR.

Example

A telecom company maps the flow of customer usage records: collected at network elements, transmitted to a cloud analytics platform, processed into billing data, and stored for audit. The map reveals one leg where records crossed a non-UK region in transit, which the company reroutes to keep the entire flow within approved jurisdictions.

2.2 Cloud data storage architectures Study guide reference: Maps to Chapter 3, Cloud Data Security (Cloud Storage Architectures and threats to storage sections).

Storage types and the threats each one faces

Each cloud service category offers its own storage types, and each type has a distinct threat profile. The exam tests whether you can match the storage type to its service model, its typical use, and its characteristic risk.

Ephemeral storage

Temporary storage that persists only while the instance is running, commonly implemented in RAM or other volatile memory, and wiped when the instance terminates. Associated with IaaS. Typical use is short lived working data such as session state. The characteristic risk is data loss on unexpected termination, and residual data if the underlying resources are reassigned without proper sanitisation.

Raw storage

Direct access to the underlying physical or block level storage media, without a filesystem or higher abstraction imposed by the provider. It offers maximum control and performance for specialised workloads, and correspondingly places responsibility for structure, management, and protection on the customer.

Volume storage

Persistent storage that emulates a physical drive attached to a cloud instance. Associated with IaaS. Typical use is databases, application files, and anything that must survive instance reboots. The characteristic risks are unauthorised access and breach where encryption and access controls are weak.

Object storage

Data managed as discrete self contained objects, each holding the data itself, its metadata, and a unique identifier, in a distributed storage environment. Associated with IaaS and PaaS. Typical use is large volumes of unstructured data such as images, video, and backups. Characteristic risks are unauthorised access, data manipulation, and compliance violations where management practices drift from regulatory requirements. Misconfigured public access on object storage is one of the most common real world causes of cloud data exposure.

Database and BLOB storage

Structured storage such as SQL databases, and Binary Large Objects for big unstructured files, associated with PaaS. Typical use is applications needing structured query access, and storage of large media or document files. The characteristic risks are SQL injection against the structured side and unauthorised access to the unstructured side.

SaaS storage

Storage wholly managed by the provider behind a SaaS application, often specialised for that application. The customer interacts with data only through the application interface. The characteristic risk is loss of control: the customer depends entirely on the provider's controls and has limited visibility into how storage is secured.

Long-term storage

Archival storage tiers designed for infrequently accessed data retained over years, trading retrieval speed for low cost. The characteristic considerations are retrieval delay, key management over long periods, and ensuring archived data remains readable and compliant for its whole retention life.

Example

An energy company's monitoring platform uses all of these at once: sensor readings buffer in ephemeral storage on the processing instances, the application database sits on volume storage, raw historical readings land in object storage, the reporting application is SaaS with its own managed storage, and seven year compliance archives go to a long-term tier. A single "where is our data" question has at least five answers, each needing its own controls.

General threats across storage types

  • Unauthorised access, mitigated with strong authentication, comprehensive access controls, and encryption at rest and in transit.
  • Regulatory noncompliance, mitigated by aligning storage configuration with the regulations that apply to the data, and auditing regularly.
  • Jurisdictional issues, mitigated by knowing where data may legally be stored and using the provider's geographic controls to keep it there.
Watch this in the exam

Match the storage type to its service model. Ephemeral and volume belong to IaaS. Object spans IaaS and PaaS. Database and BLOB belong to PaaS. If a question pairs SQL injection with a storage type, it is pointing at database storage. If it pairs session state or volatile memory with a type, it is pointing at ephemeral.

2.3 Data security technologies and strategies Study guide reference: Maps to Chapter 3, Cloud Data Security (encryption, hashing, masking, tokenization, and DLP sections).

Encryption, hashing, obfuscation, tokenization, DLP, and secrets management

Encryption levels in cloud environments

Encryption can be applied at several levels, and the level chosen determines who is protected against whom.

  • Application-level encryption, implemented inside the application itself, encrypting data as the user enters it, before it ever reaches storage.
  • Database-level encryption, protecting whole database files or specific columns and tables. Particularly effective in PaaS where the customer controls the encryption keys.
  • File-level encryption, performed by client applications at the filesystem level, encrypting and decrypting files on the fly under the user's control, which protects data from other tenants and from provider personnel.
  • Volume-level encryption, encrypting an entire data volume, with keys managed by the customer, protecting against physical theft and against access by provider staff or other tenants.
Example

A bank encrypts card numbers at the application level before they reach the database, encrypts the sensitive columns of the database itself, and runs the whole database on an encrypted volume. Three layers, three different attackers defeated: an application layer eavesdropper, a database administrator overreaching, and someone with access to the underlying storage.

Key management

Encryption is only as strong as the management of its keys. A cloud Key Management System (KMS) handles cryptographic operations and the key lifecycle inside a secure boundary. Customer Managed Encryption Keys (CMEK) let the customer control its own keys while integrating with the provider's KMS, which matters for compliance regimes that require customer key custody.

The key lifecycle runs: creation, using cryptographically secure random generation; storage, in encrypted vaults or hardware security modules with tightly restricted access; usage, under defined protocols with all use logged and monitored; sharing, discouraged, and done only through secure channels when unavoidable; and archiving, retaining retired keys securely where they are still needed to decrypt historical data. Keys must be stored separately from the data they protect, and rotated on a schedule so a compromised key has a limited exposure window.

Watch this in the exam

If a scenario stores keys alongside the encrypted data, that is the flaw, whatever else the question says. And remember why archived keys exist at all: destroying a key that still protects archived data is equivalent to destroying the data, which is exactly what cryptographic erase exploits deliberately.

Hashing

Hashing is often described as one way encryption, though strictly it is not encryption at all, because it is not reversible. A hash function takes input of any length and produces a fixed unique hash value. Comparing hash values computed at two points in time proves whether data changed, which is why hashing serves the integrity principle: verifying the accuracy of backups, confirming messages arrived unaltered, and detecting file changes that indicate system compromise.

Hashing also underpins digital signatures, which deliver non-repudiation. The signer computes a hash of the data and encrypts that hash with their private key. The recipient computes their own hash of what arrived and decrypts the signature with the signer's public key. Matching values prove both that the data is unaltered and that it came from the holder of the private key, who cannot later deny having signed it.

Example

A telecom company integrates a third party software library into its cloud platform. Before deployment, the build pipeline verifies the library's digital signature against the vendor's public key. A mismatch would mean the package was altered after signing, or never came from the vendor at all, and the deployment stops.

Data obfuscation

Obfuscation, also called de-identification or masking, produces data that looks and behaves like the original without exposing the sensitive values, typically so testers, developers, or researchers can work without being authorised to see live data. Regulations often mandate it when data is used beyond its original operational purpose. Common methods include substitution, replacing values with other data, either randomly or following integrity rules; shuffling, rearranging real values within a column so each value is genuine but attached to the wrong record; and value variance, applying mathematical changes to numerical data such as dates or amounts. Encryption is a poor fit for this purpose, because encrypted data is unreadable and therefore useless for testing.

Example

A bank refreshes its test environment from production monthly. Customer names are substituted with synthetic ones, account numbers are shuffled within the column, and balances have a small random variance applied. The test data still exercises every code path realistically, but no tester ever sees a real customer's real balance.

Anonymization

Anonymization goes further than masking: it aims to remove the link between the data and the individual permanently, including the indirect identifiers that could re-identify someone when combined. Done properly, anonymized data falls outside many privacy regimes entirely. The difficulty is that true anonymization is hard, because seemingly harmless attributes in combination can re-identify individuals.

Tokenization

Tokenization substitutes a sensitive data element with a non-sensitive token. It is not encryption: rather than obscuring data with a key, it removes the sensitive value from the environment entirely and stores it in a separate, tightly controlled token vault. The application keeps only the token. When an authorised process needs the real value, it presents the token to the tokenization server, which checks identity and authorisation before returning the original. The classic application is payment cards, where merchants hold tokens rather than card numbers, drastically shrinking their compliance scope under PCI DSS.

Example

A retail bank's mobile app displays a saved card as a token ending in the same four digits. The real card number lives only in the token vault, behind its own access controls. A breach of the app's database yields tokens that are worthless outside the bank's own tokenization system.

Watch this in the exam

Keep the trio straight. Masking produces realistic fake data for use in place of the real thing. Tokenization removes the real value to a vault and leaves a reversible reference. Anonymization severs the link to the individual permanently. If reversibility through a secure mapping is described, the answer is tokenization. If the goal is test data, the answer is masking. If the goal is escaping privacy regulation entirely, the answer is anonymization, along with a healthy scepticism about whether it was truly achieved.

Data Loss Prevention

DLP, also called data leakage prevention, is a set of controls that keep defined types of data, structured and unstructured, inside the organisation's control in line with policy. Its primary function is detecting and preventing unauthorised exfiltration of sensitive data such as account numbers and national identifiers. A DLP capability has three components: policy management, defining what data is protected and how; monitoring and enforcement, watching data at rest and in transit and acting on violations; and incident response, handling what happens when a violation is detected.

Example

An energy company's DLP policy flags any outbound email containing grid asset identifiers. When an engineer attaches a substation schematic to a message addressed outside the company, the DLP engine blocks the send, notifies the security team, and logs the incident, all before the data leaves.

Keys, secrets, and certificates management

Beyond encryption keys, cloud environments run on secrets, meaning API keys, passwords, tokens, and connection strings, and on digital certificates. A secrets manager centralises storage of these values with access control and audit logging, replacing the dangerous habit of embedding credentials in code or configuration files. A certificate manager handles the lifecycle of digital certificates and the secure handling of their private keys, including issuance, renewal, and revocation. Centralising both means credentials can be rotated, audited, and revoked in one place.

Example

A maritime company's deployment pipeline once held database passwords in a configuration file inside the code repository. Anyone with repository access could read production credentials. Moving them into a secrets manager meant the pipeline retrieves credentials at run time, every retrieval is logged, and rotating a compromised password is one change in one place rather than a hunt through every repository.

2.4 Data discovery Study guide reference: Maps to Chapter 2, Data Classification (data discovery and data types sections).

Finding data before you can protect it

You cannot classify, protect, or delete data you do not know you have. Data discovery is the process of locating data across an organisation's estate, and it depends on understanding the three structural forms data takes.

Structured data

Data with a predefined format and content type, organised into distinct fields, the classic example being a relational database. Its defining attributes are a defined structure, validation before storage, ease of search, and strong suitability for analysis. Discovery in structured data is comparatively straightforward, because the schema itself describes what each field contains.

Unstructured data

Data with no imposed structure or format: documents and text files, emails, images, videos, office documents, and scientific datasets. Unstructured data is the hardest to discover and govern, because nothing about its container reliably describes its contents. A spreadsheet named notes.xlsx can hold anything from a lunch rota to a full customer export.

Semi-structured data

The middle ground: data that uses markers or tags to delineate semantic elements and hierarchies, without conforming to a rigid tabular schema. XML and JSON are the canonical examples, widely used for data interchange and in object oriented databases. It may carry metadata tags for attributes such as location, date, or source, while the content inside the tags remains unstructured.

Example

A telecom company's customer records sit in a relational database (structured), its call centre voice recordings sit in object storage (unstructured), and the data feeds it exchanges with partner networks are JSON documents (semi-structured). A subject access request under GDPR has to find the customer in all three, which is precisely why discovery tooling must handle every form.

Data location

Cloud mobility means customers often do not know precisely where their data physically sits, and for routine operations that may not matter. It matters greatly for regulated and sensitive data, where compliance depends on knowing and controlling location. Organisations with legal, compliance, or operational reasons should define a preferred data location, use the provider's geographic controls to enforce it, and engage the provider proactively for clarity on where data is actually stored, including replicas and backups.

Watch this in the exam

Discovery questions often hinge on matching the data form to the discovery difficulty. Structured data is easiest because the schema is self describing. Unstructured is hardest and is where most undiscovered sensitive data hides. If a question mentions tags, markers, XML, or JSON, it means semi-structured.

2.5 Data classification Study guide reference: Maps to Chapter 2, Data Classification (classification policies, data mapping, and labeling sections).

Classification policies, mapping, and labeling

Data classification policies

A data classification policy is the framework of procedures, processes, and guidelines by which an organisation categorises stored information by sensitivity. Its purposes are consistent handling, guidance across the entire data lifecycle from creation to disposal, and risk reduction against privacy breaches, compliance violations, and security incidents. Two properties matter: the policy must be tailored to the organisation, since a bank's categories will not fit a logistics firm, and it must align with the laws and regulations that apply to the data.

Example

A bank defines four levels: public, internal, confidential, and restricted. Each level carries defined handling rules, storage requirements, sharing constraints, and destruction methods. Marketing material is public. Board papers are restricted. The point is not the labels themselves but that every employee handling a document knows, from its level alone, exactly what they may and may not do with it.

Data mapping

Data mapping builds the picture of where data resides across applications and storage infrastructure. Discovery software scans data sources using a range of attributes, the most important being metadata, meaning data about data: details of a file's creator, origin, format, and context. A sound mapping strategy lets the organisation identify precisely where data lives, which is the foundation for governance, and for enforcing security policy, since you can only protect what the map shows you.

Data labeling and tagging

Labeling attaches identifying information to data, typically covering attributes such as department, location, and creator, and often carrying the classification itself, with labels such as confidential or restricted. Digital data cannot carry a physical sticker, so labeling uses methods such as metadata tagging, associating descriptive metadata with the asset, and header labels, embedding the label in the file's header for quick identification. Labels are what allow automated controls, such as DLP, to act on classification: the policy says restricted data may not leave, and the label is how the tooling recognises restricted data when it sees it.

Example

An energy company's document management system stamps a classification label into the metadata and header of every file at creation. Months later, when someone attaches a restricted engineering drawing to an outbound email, the DLP engine does not need to understand the drawing. It reads the label and blocks the send. Classification did the thinking at create time; the label carried the decision forward.

Watch this in the exam

Keep the sequence straight: discovery finds the data, classification decides its sensitivity, mapping records where it lives, and labeling attaches the decision to the data so controls can enforce it. Questions that ask what must happen first are usually pointing at discovery or classification, depending on whether the scenario is about finding data or deciding how to treat it.

2.6 Information Rights Management Study guide reference: Maps to Chapter 2, Data Classification (Information Rights Management section).

IRM objectives and the certificate machinery behind it

Objectives

Information Rights Management extends protection beyond standard encryption by attaching access control to the data object itself. Its key objectives:

  • Layered access control, an additional control layer over documents and data objects that determines not just who can open a file but what they may do with it: printing, saving, copying, forwarding. This granularity is an application of least privilege to individual actions on a document.
  • Provisioning and access models, defining how rights are granted to users and roles, and how those rights are managed over the document's life.
  • Location agnosticism, the defining IRM property: the access control list is embedded in the file itself, so protection travels with the data wherever it goes. This is precisely what makes IRM suited to cloud environments, where data moves constantly between locations the organisation does not control.
  • Protection across data types, covering financial documents, emails, database columns, web pages, and other objects, making IRM a foundation of information protection policy for critical assets.
Example

A maritime company shares a commercially sensitive charter agreement with an external broker. IRM permits the broker to read the document but not print, copy, or forward it, and the restriction holds even after the file leaves the company's systems, because the rights are embedded in the file. When the deal closes, the company revokes access centrally, and the copy sitting in the broker's inbox becomes unreadable.

Watch this in the exam

The IRM versus DLP boundary is a favourite. DLP watches channels and stops sensitive data leaving. IRM travels with the object and controls use after it has left. If the scenario needs control over a file already outside the organisation, DLP cannot help; the answer is IRM.

Appropriate tools: certificates, issuance, and revocation

IRM implementations depend on identity, and identity at scale depends on Public Key Infrastructure. The exam focus is on revocation, the mechanism that ends trust in a certificate before its natural expiry.

  • Certificate Revocation List (CRL), a list maintained by the Certificate Authority holding the serial numbers of revoked certificates and their revocation times. Clients download and parse the CRL to check a certificate's status. CRLs are distributed through defined channels and have expiry times, and parsing large CRLs is resource intensive, which is why some systems cache them.
  • Online Certificate Status Protocol (OCSP), the alternative to CRLs: a real time query to the CA or an OCSP responder about one specific certificate, giving a more immediate answer without downloading the whole list.
Example

A contractor's access certificate is compromised on a Friday. The CA revokes it immediately. A system relying on a weekly CRL download might trust that certificate until the next refresh, while a system using OCSP asks in real time and rejects it within minutes. The trade is freshness against the overhead of a query per check.

2.7 Retention, deletion, and archiving Study guide reference: Maps to Chapter 2, Data Classification (retention, deletion, archiving, and legal hold sections).

Keeping data as long as required, and no longer

Data retention policies

A retention policy sets out how long information is kept to satisfy regulatory, legal, and business requirements, balanced against the cost and complexity of storing it. Its objectives include compliance, cost management by disposing of data that is no longer needed, risk reduction by not holding sensitive data longer than necessary, and ensuring retained data stays accessible and retrievable. A complete retention policy defines:

  • Purpose and scope, what the policy is for, which data types it covers, and which parts of the organisation it applies to.
  • Retention periods, specific schedules per data type, grounded in legal, regulatory, and business requirements.
  • Roles and responsibilities, who implements and oversees the policy: data managers, IT, legal, department heads.
  • Storage, security, and access, how data is protected during retention and how it can be retrieved.
  • Disposal procedures, how data is securely and irrecoverably destroyed when its period expires.
  • Review, training, and audit, mechanisms to keep the policy current, staff aware, and compliance verifiable.
Example

A bank retains transaction records for the period its regulator requires, then destroys them on schedule. Keeping them longer is not generosity, it is risk: every extra year of retained personal data is another year it can be breached, subpoenaed, or fall within the scope of a subject access request. A good retention policy treats deletion on schedule as seriously as retention on schedule.

Data deletion procedures and mechanisms

Deletion procedures define how data is actually destroyed when retention ends, and they must produce irrecoverable results proportionate to the data's sensitivity. In the cloud, where the customer cannot physically destroy media, the practical mechanisms are overwriting and cryptographic erase, with cryptographic erase, destroying the key that protected the data, being the standard answer for multi-tenant storage the customer cannot touch.

Data archiving procedures and mechanisms

Archiving identifies inactive data and moves it into specialised long term storage, which keeps primary systems fast and storage costs down. The elements of an archiving policy include data encryption procedures for the archive, data monitoring, the ability to perform e-discovery against archived content when legal proceedings demand it, and backup and disaster recovery arrangements for the archive itself. The long time horizon is what makes archiving distinctive: keys age, formats age, and the archive must remain both secure and readable for its whole life.

Legal hold

A legal hold preserves data in response to actual or anticipated legal proceedings, triggered by a judicial or law enforcement order. Its key aspects: the hold notice defines the scope of data that must be preserved; the duration normally runs until proceedings conclude; the organisation may be required to keep custody and protection of the data, safeguarding it from alteration or destruction; and some situations impose escrow or independent custody requirements, placing the data with a neutral party.

Example

An energy company receives a hold notice covering all correspondence about a disputed contract. Some of those emails are three weeks from automated deletion under the retention policy. The hold overrides the schedule: deletion is suspended for everything in scope until the litigation ends. Letting the automated deletion run would be spoliation of evidence, with consequences far worse than the storage bill.

Watch this in the exam

Legal hold always beats the retention schedule. Any scenario where scheduled deletion is about to destroy data under hold has one right answer: suspend the deletion for the data in scope. Every distractor that lets the deletion proceed, archives quietly, or asks the provider to delete early is describing evidence destruction.

2.8 Auditability, traceability, and accountability of data events Study guide reference: Maps to Chapter 3, Cloud Data Security (auditability, traceability, and accountability of data events section).

Event sources, logging, and proving who did what

Event sources and event attributes

An event source is any software, hardware, or system that generates activity logs: operating systems, applications, network devices, cloud platform services. Identifying event sources is the first step in monitoring, incident detection, and compliance, because you can only analyse what something actually recorded. Event attributes are the details each event must carry to be meaningful. The attributes the outline names are identity, who or what performed the action; IP address, where the request came from; and geolocation, the physical origin. In practice a useful event also carries a timestamp and the action performed. Rich attributes are what turn a log line into evidence: they support troubleshooting, security analysis, auditing, and compliance reporting.

Example

A bank investigates an unusual bulk download from its document platform. The event log shows the identity used, the source IP, a geolocation inconsistent with the employee's location, and the exact objects accessed with timestamps. Those attributes let the team reconstruct the incident hour by hour. Without them, the log would say only that something happened.

Logging, storage, and analysis of data events

Three interconnected activities. Logging records events as they occur. Storage keeps logs secure and intact for a defined retention period, which is often itself a regulatory requirement, and protects them from tampering, since an attacker's first move is frequently to alter the logs. Analysis turns stored logs into insight: identifying trends, diagnosing issues, and detecting anomalies that indicate security incidents. Each depends on the previous: analysis is only as good as what was logged, and logs are only trustworthy if storage preserved them unaltered.

Chain of custody and non-repudiation

Chain of custody is the documented record of how evidence has been collected, handled, stored, and transferred, capturing who touched it, when, and why. A rigorous chain establishes the integrity and credibility of evidence, demonstrating it could not have been tampered with, which is what makes it admissible in court. Non-repudiation is proof that a specific action or communication genuinely originated from a specific party, who cannot later deny it. Digital signatures are the standard mechanism: only the holder of the private key could have signed, so the signature is proof of origin and integrity together. Non-repudiation matters wherever denial would be damaging: financial transactions, contract signing, and system administration actions.

Example

A maritime company suspects an insider altered cargo manifests. The forensic copy of the storage is hashed at collection, every transfer between investigators is logged with names and timestamps, and the analysis is performed on verified copies. When the case reaches an employment tribunal, the chain of custody shows the evidence is exactly what was collected, and the digitally signed change records prove which account made each alteration.

Watch this in the exam

Chain of custody is about the handling of evidence after the fact. Non-repudiation is about proving the origin of an action at the time it happened. Hashing serves integrity, digital signatures serve non-repudiation, and the documented handling record serves admissibility. Questions frequently swap these three, so anchor each mechanism to its purpose.

2.9 Data protection for AI and ML Study guide reference: New to the exam outline as of August 2026. The 3rd Edition study guide predates this subtopic and does not cover it. Treat this section as a standalone supplement.

Protecting the data that trains and feeds AI systems

This subtopic was added to the outline in the August 2026 update. It treats AI training data and the models themselves as data assets requiring the same discipline as any other sensitive data, plus some protections unique to machine learning. The outline names two areas: data set and model privacy, and data set and model security through validation and verification.

Data set and model privacy

Training data often contains personal information, and a trained model can leak what it learned. An attacker querying a deployed model repeatedly can sometimes infer whether a specific individual's record was in the training set, or reconstruct attributes of that record. Two technical controls address privacy at this level. Differential privacy adds calibrated statistical noise so that a model's outputs do not reliably reveal any individual training record, protecting privacy during the inference phase. Homomorphic encryption allows computation to be performed on data while it remains encrypted, so sensitive data can be processed, including by a model, without ever being exposed in plain form.

Example

A bank's fraud model is trained on real transaction histories. Without protection, a determined adversary querying the model's risk scores could infer details about specific customers' transactions. Applying differential privacy to the model's outputs means each answer carries enough statistical noise that no individual customer's history can be reconstructed, while the model remains accurate in aggregate.

Data set and model security: validation and verification

The security of an AI system rests on the integrity of its data pipeline. Validation checks that training data is accurate, representative, and free of corruption before it is used. Verification confirms the data's provenance and integrity, that it came from trusted sources and has not been tampered with. Together they defend against data poisoning, where an adversary corrupts the training set to change the model's behaviour. The same discipline applies at inference time, since a model in production continues to consume data that can be manipulated.

Large training sets commonly live in data lakes, which concentrate enormous volumes of raw data and therefore concentrate risk: a poorly governed lake mixes sensitive and non-sensitive data with weak visibility. Discovery and classification tooling, increasingly AI assisted itself, identifies sensitive information before it enters an ML pipeline. Two further concerns round out the picture. Data sovereignty applies when training data is processed across multiple cloud regions, since each jurisdiction's rules follow the data. And data remanence applies to the ephemeral storage used by AI compute nodes: training residuals left on de-provisioned nodes must be purged, typically by cryptographic erase, before the resources return to the shared pool.

Example

A telecom company trains a churn model on customer data in a cloud data lake. Before training, discovery tooling scans the lake and flags fields containing personal data, which are masked. The pipeline verifies each source feed's integrity by checksum before ingestion. Training runs in a region-restricted environment to satisfy UK data residency, and when the training cluster is torn down, the ephemeral volumes are cryptographically erased so no fragment of customer data survives on the recycled hardware.
