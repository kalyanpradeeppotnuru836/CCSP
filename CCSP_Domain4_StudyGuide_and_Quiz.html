4.1 Training and awareness for application security Study guide reference: Maps to Chapter 6, Cloud Application Security (training and awareness, common pitfalls, and common vulnerabilities sections). Building a security-aware development culture

Cloud development basics

The Cloud Security Alliance and SAFECode identify collaborative accountability as the foundation of a security-conscious development programme, built on three components:

  • Security by design, treating security as a fundamental consideration at every stage, from initial feasibility through to retirement, rather than an afterthought or a reaction to a discovered flaw.
  • Shared security responsibility, where everyone from senior management to the newest team member holds accountability, rather than security being one team's problem.
  • Security as a business objective, where security is central to business operations rather than a part of them, and every business goal carries a security element.

Common pitfalls

The primary pitfall is failure to secure immediate and ongoing support from upper management. If senior leadership does not approve and adhere to security policies, and does not adequately fund and staff security work aligned to organisational goals, efforts to build a security culture will fail. Other recurring pitfalls include not understanding the organisation's culture, since even businesses in the same sector differ; inconsistency across teams when no established secure development framework exists; and cutting training programmes when there is no immediate consequence. A committed organisation finds ways to sustain awareness training under financial pressure, for example through online course subscriptions rather than abandoning it.

Example

A bank mandates secure coding standards but does not fund the training or give teams time to apply them. Developers meet delivery deadlines by treating the standard as optional. The policy exists on paper and fails in practice, which is exactly what inadequate leadership commitment produces.

Common cloud vulnerabilities and the reference lists

Cloud's reliance on network systems exposes it to data breaches, compromised integrity, insecure APIs, and denial of service, with applications and transmissions operating in potentially hostile environments. Five reference lists are named in the outline, and you should know what each covers:

  • OWASP Top 10, the widely used list of the most critical web application security risks, including broken access control, cryptographic failures, injection, insecure design, and security misconfiguration.
  • OWASP Application Security Verification Standard (ASVS), a framework for evaluating the technical security measures in web applications, establishing a balanced and standardised approach to verification.
  • OWASP Top 10 API Security Risks, focused specifically on API weaknesses such as broken object level authorisation and excessive data exposure, which differ from traditional web application risks.
  • OWASP Top 10 for Large Language Model Applications, new to this outline, covering risks such as prompt injection, insecure output handling, training data poisoning, model denial of service, and supply chain vulnerabilities in models and datasets.
  • SANS Top 25, the most dangerous software errors, oriented toward coding weaknesses rather than deployed application risks.
Watch this in the exam

Do not confuse prompt injection with insecure output handling. Prompt injection is crafted input manipulating the model into ignoring its instructions. Insecure output handling is the application failing to sanitise what the model produced before using it downstream. They sit at opposite ends of the same request, and questions often describe one while offering both.

4.2 The Secure Software Development Life Cycle Study guide reference: Maps to Chapter 6, Cloud Application Security (SDLC business requirements, phases, and methodologies sections).

Requirements, phases, and methodologies

Business requirements

Gathering, reviewing, and understanding business requirements is essential to meeting organisational goals and customer expectations, whether for a new system or an improvement to an existing one. At conception, the requirements must rest on a comprehensive understanding of the project's necessity, its objectives, and its target audience, and should incorporate feedback from as many stakeholders as possible. Security requirements belong in this gathering alongside functional ones, because a requirement discovered late costs far more to satisfy than one captured at the start.

Phases

Any SDLC, including a secure SDLC, runs through a common set of phases: requirements gathering, design, development or coding, testing, deployment, and maintenance through to eventual retirement. What makes an SSDLC distinct is that security activity attaches to every phase rather than appearing only at testing.

Methodologies

  • Waterfall, a sequential and linear approach where each phase completes before the next begins. Predictable and well documented, but slow to accommodate change once underway.
  • Agile, iterative and incremental, delivering working software in short cycles and adapting to changing requirements. Security must be embedded in each iteration rather than deferred.
  • Spiral, iterative with explicit risk analysis at each cycle, making it well suited to projects where risk must be actively managed.
  • DevOps, the more recent approach enhancing deployment frequency and speed by integrating development and operations, with DevSecOps adding security into that integration.
Example

A telecom company building a regulated billing platform uses waterfall, because the requirements are fixed by regulation and a documented sequential trail supports the audit. Its customer-facing app team uses agile, because requirements shift with market feedback. Both need security in every phase; only the cadence differs.

4.3 Applying the Secure SDLC Study guide reference: Maps to Chapter 6, Cloud Application Security (cloud-specific risks, threat modeling, secure coding, and configuration management sections).

Cloud-specific risks, threat modeling, secure coding, and configuration management

Cloud-specific risks

Risks that arise specifically from using cloud services include data breaches; insufficient identity, credential, and access management; insecure interfaces and APIs; system vulnerabilities; compliance risks; data sovereignty; vendor lock-in; service reliability; scalability issues; cost management; and integration challenges. The outline also names shared technology issues, provider insider threats, lack of visibility and control, and legal and jurisdictional issues.

Threat modeling techniques

Four techniques are named, and the exam relies on you distinguishing what each actually does:

  • STRIDE, a categorisation scheme identifying threats as Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, or Elevation of Privilege. It tells you what kinds of threat exist.
  • DREAD, a rating scheme scoring identified threats on Damage potential, Reproducibility, Exploitability, Affected users, and Discoverability. It tells you how serious each threat is, so it follows identification rather than replacing it.
  • ATASM, Architecture, Threats, Attack Surfaces, and Mitigations, working from the architecture outward to identify where the system can be attacked and what should defend it.
  • PASTA, the Process for Attack Simulation and Threat Analysis, a seven-stage risk-centric methodology aligning technical threats to business objectives through attacker-focused simulation.
Watch this in the exam

STRIDE categorises, DREAD scores. If a scenario is identifying what could go wrong, it wants STRIDE. If it is prioritising threats already found, it wants DREAD. PASTA is the seven-stage business-aligned one; ATASM starts from architecture and attack surfaces.

Secure coding standards

OWASP ASVS provides a comprehensive framework for evaluating the technical security measures in web applications, giving development and testing teams a common, standardised basis for verification. SAFECode is a forum where company executives and technical experts share knowledge and collaborate on developing, improving, and promoting scalable and effective software security programmes, helping businesses establish or improve their own.

Software configuration management and versioning

Versioning and configuration management matter for any system, and take on added significance in cloud because rapid provisioning and self-elasticity make it easy for environments to drift apart. System stability and cohesiveness become paramount. In traditional data centres, upgrades and patches are applied directly to existing servers and hosts. In cloud, the immutable pattern is preferred: deploy a new, correctly configured instance and retire the old one, so that every running instance matches a known version rather than accumulating undocumented change.

Example

An energy company's auto-scaling group launches new instances from an image. If patches are applied by hand to running machines, every scale-up event reintroduces the unpatched image, and the fleet silently diverges. Rebuilding the image and replacing instances keeps every machine identical and traceable to a version.

4.4 Cloud software assurance and validation Study guide reference: Maps to Chapter 6, Cloud Application Security (testing, quality assurance, and abuse case sections). SAST, DAST, IAST, and SCA are named in the current exam outline and are covered here alongside the white, grey, and black-box perspectives.

Testing what was built, and testing how it can be abused

Functional and non-functional testing

Functional testing is a focused assessment of a particular function or component, checking that the system does what its functional requirements say it should. In cloud projects this carries extra considerations, notably understanding the legal and regulatory requirements that apply. Non-functional testing covers the aspects functional testing does not: performance, usability, and dependability. Where functional testing examines precise behaviours against requirements, non-functional testing establishes how the system performs and whether it is ready for use.

CI/CD processes automate build, test, and deployment so that changes are validated continuously rather than in a large batch before release, which is what makes frequent secure delivery practical.

Knowledge-based testing perspectives

  • White-box testing, conducted with full knowledge of the internal structure, source code, and design.
  • Grey-box testing, conducted with partial knowledge, typically some design or architecture information but not full source access.
  • Black-box testing, conducted with no internal knowledge, approaching the system as an external attacker would.

Security testing methodologies

These are the tool-based methodologies named in the outline, and they are distinguished by what they examine and when:

  • SAST, Static Application Security Testing, analyses source code or binaries without executing them. It finds coding flaws early but cannot see runtime or configuration issues, and produces false positives for code paths that are never reachable.
  • DAST, Dynamic Application Security Testing, tests the running application from the outside without source access, finding runtime and configuration issues that static analysis misses, but only in the paths it manages to exercise.
  • IAST, Interactive Application Security Testing, instruments the running application so it observes behaviour during execution with visibility into the code, combining elements of both static and dynamic approaches.
  • SCA, Software Composition Analysis, identifies third-party and open-source components and flags those with known vulnerabilities or problematic licences. It examines what you imported rather than what you wrote.
Watch this in the exam

Anchor each to what it inspects. SAST reads code without running it. DAST attacks the running app without reading code. IAST instruments the running app and sees both. SCA looks at dependencies, not your own code. A question about a vulnerable third-party library wants SCA, not SAST.

Quality assurance and abuse case testing

QA encompasses planning, evaluation, and inspection to guarantee the constructed system meets its quality requirements, applying across all cloud deployment models. Abuse case testing inverts the perspective: rather than confirming the software does what it should, testers compile a list of known misuse cases and actively attempt to exploit them using manual or automated attack techniques. It asks what an attacker would try, not what a user is meant to do.

Example

A use case says a customer can transfer funds between their own accounts. The matching abuse case asks what happens if the account identifier is changed to someone else's, if the amount is negative, or if the request is replayed. Functional testing passes the use case; abuse case testing is what finds the broken authorisation check.

4.5 Using verified secure software Study guide reference: Maps to Chapter 6, Cloud Application Security (API security, supply chain, and third-party software sections), with vendor management material in Chapter 10.

APIs, supply chain, third-party software, and open source

Securing APIs

API security is central to overall application security. Introducing inadequately secured APIs, particularly when integrating APIs outside the application's own control or security boundary, poses significant risk and can jeopardise the entire dataset within the application, leading to exposure or loss. Practical controls include strong authentication and authorisation on every endpoint, input validation, rate limiting and throttling, TLS for all traffic, and careful review of what each endpoint returns, since excessive data exposure is a leading API weakness.

Supply chain management

Supply chain management has two aspects. First, a provider, and potentially the customer, will engage third-party providers to deliver services, so a provider often relies on other vendors to supply what its customers ultimately consume. This encompasses vendor risk management when establishing those relationships. Second, cloud itself extends the reach of supply chain management, since globally interconnected supply chains need access to primary and secondary sources and cloud infrastructure improves the efficiency of coordinating them. The security concern is that your risk extends through providers you have no contract with.

Example

A bank contracts with a SaaS vendor that depends on a third-party analytics service, which in turn runs on another provider's infrastructure. The bank has a contract with one party but exposure through three. Vendor assessment must ask what the vendor's own dependencies are, not just what the vendor does.

Third-party software management and open source

Cloud shifts software from local installation toward remote hosted services, which changes how licensing works: cloud-based licensing is efficient enough that end users often need not navigate separate licence processes, making licensing effectively invisible from their perspective. That convenience does not remove the obligation to track what is in use.

Open-source software is pervasive in cloud, with developers relying on open-source applications, toolsets, and frameworks. What distinguishes the most widely used packages is the rigour of their development process, including peer review and active maintenance. Validated open source means components that have been assessed for provenance, maintenance status, and known vulnerabilities before adoption, rather than pulled in simply because they solve the immediate problem. Software Composition Analysis and a maintained Software Bill of Materials are the practical mechanisms for keeping that inventory current.

4.6 Cloud application architecture Study guide reference: Maps to Chapter 6, Cloud Application Security (supplemental security devices, cryptography, sandboxing, and application virtualization sections).

Supplemental components, cryptography, sandboxing, and orchestration

Supplemental security components

These devices augment a defence-in-depth architecture, where multiple overlapping layers of security mutually reinforce one another.

  • Web Application Firewall (WAF), a layer 7 firewall that understands HTTP traffic and can block application-layer attacks such as injection and cross-site scripting.
  • Database Activity Monitoring (DAM), a layer 7 monitoring device that understands SQL commands and detects anomalous or unauthorised database activity.
  • XML firewall, inspecting XML traffic and protecting against XML-specific attacks such as malformed documents and entity expansion.
  • API gateway, centralising authentication, rate limiting, and version management for APIs.
  • Load balancer, distributing traffic across backend instances, which supports availability and can terminate TLS.
Watch this in the exam

WAF understands HTTP, DAM understands SQL. Both operate at layer 7 but inspect different protocols, and questions frequently offer both. If the scenario concerns web request content, it wants a WAF; if it concerns database queries and access patterns, it wants DAM.

Cryptography

Cloud systems operate across trusted and untrusted networks, which can be described as hostile or semi-hostile environments, so encryption is essential for data stored within and transmitted between cloud services. Three encryption scopes are distinguished:

  • Whole instance encryption, encrypting all data associated with the operation and use of a virtual machine.
  • Volume encryption, encrypting a single volume on a drive.
  • File or directory encryption, encrypting an individual file or directory.

Sandboxing

Sandboxing is the segregation and isolation of information or processes within the same system or application for security purposes. It isolates different communities and user populations from one another's data, and the requirement can be driven internally by organisational policy or externally by regulation. It is also the standard technique for safely executing untrusted code or analysing suspected malware.

Application virtualisation and orchestration

Infrastructure virtualisation underpins cloud computing, while containerisation underpins many cloud application architectures including microservices. Containers separate corporate data and software from the user's device, which lets an organisation remotely wipe corporate data, applications, and access without touching the employee's personal content, a meaningful protection for both parties. Orchestration software manages containers and applications at scale and plays a critical role in enforcing security and compliance with the organisation's secure computing policies, letting customers oversee all their cloud resources from a central platform. Kubernetes is the dominant orchestration platform, and securing it, along with the container registry and the images themselves, is part of securing the application.

4.7 Identity and Access Management solutions Study guide reference: Maps to Chapter 6, Cloud Application Security (identity and access management, federated identity, and multifactor authentication sections).

Federation, identity providers, SSO, MFA, CASB, and secrets

Federated identity

Federated identity works much like single sign-on, with one digital identity granting access to multiple systems, but it extends across boundaries: a federated identity can reach applications across different cloud providers, multi-cloud resources, and on-premises systems, and it enables single sign-on across systems belonging to different organisations. Both the on-premises IAM system and the IAM systems of each cloud vendor must be closely safeguarded against unauthorised use. Federation carries the same drawback as SSO in amplified form: when one federated system is compromised, that compromise exposes vulnerabilities across all the federated systems.

Identity providers

An identity provider may be a provider's own service or a third-party service. In multi-cloud scenarios a third-party identity provider is often the most efficient choice, since it gives one unified solution across providers rather than several separate ones. Identity providers complement rather than replace existing cloud security technologies such as CASBs.

Single sign-on

SSO streamlines access to all approved systems within a single IAM system after one authentication, letting users move between systems without re-authenticating. Because one credential now opens many doors, monitoring all access within an SSO system is critical: a compromised digital identity puts every connected system at risk, which is precisely why SSO is normally paired with strong authentication.

Multi-factor authentication

MFA, also called strong authentication, adds verification layers by requiring at least two factors from different categories: something you know such as a password, something you have such as a token or phone, and something you are such as a fingerprint or other biometric. Two instances of the same category, such as a password and a security question, do not constitute genuine multi-factor authentication.

Example

A bank pairs SSO with mandatory MFA. SSO means one compromised password would otherwise reach every internal system, so the second factor is what keeps a phished credential from becoming a full breach. The convenience of SSO and the necessity of MFA are two sides of the same design decision.

Cloud Access Security Broker

A CASB is a software product or service positioned between an organisation's on-premises infrastructure and a cloud provider's infrastructure. Acting as a gatekeeper, it lets the organisation extend its reach beyond its own network boundaries and enforce security policy within cloud environments. Typical CASB capabilities include visibility into cloud usage including unsanctioned shadow IT, data security enforcement such as DLP across sanctioned services, threat protection, and compliance monitoring.

Secrets, key, and certificate management

Cloud secrets management covers the methods and technologies used to safeguard digital credentials in cloud environments, with accessibility and authorisation as the key priorities, noting that each cloud platform implements secrets management differently. Cloud-based secrets include API keys, SSH keys, encryption keys, passwords, private certificates, and tokens. Centralised management enables rotation, auditing, and revocation in one place, replacing credentials embedded in code or configuration files.
