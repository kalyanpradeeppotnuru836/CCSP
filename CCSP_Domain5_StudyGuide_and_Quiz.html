Getting the environment built securely in the first place

Hardware specific security configuration

Study guide: Ch 5 › Securing Hardware and Compute

Different hardware types need tailored security settings, spanning servers, workstations, routers, and switches. Typical measures include BIOS passwords to prevent unauthorised changes to system settings, disabling unused ports and services to reduce the attack surface, and configuring firewalls and intrusion detection to monitor and block malicious activity. Two hardware components carry specific exam weight:

  • Trusted Platform Module (TPM), a hardware component embedded in an individual device or server that securely stores cryptographic keys and supports platform integrity functions such as secure boot measurement.
  • Hardware Security Module (HSM), a dedicated cryptographic device used for enterprise scale key generation, storage, and cryptographic operations.
Watch this in the exam

TPM and HSM both protect keys in hardware and are routinely offered as alternatives to each other. The TPM is device or platform level, tied to integrity measurement of one machine. The HSM is an enterprise key management appliance serving many systems. If the scenario is about secure boot or attesting one machine's integrity, it wants TPM.

Network device security

Study guide: Ch 5 › Securing Communications and Infrastructure (Firewalls, IDS/IPS, Bastion Hosts)

Routers, switches, firewalls, load balancers, and wireless access points form the backbone that server and endpoint security depend on, yet they are routinely hardened less thoroughly than the systems they carry. The measures that matter most:

  • Remove default credentials. Devices shipping with a known administrative account is among the most common real world findings, and those credentials must be changed before deployment rather than afterwards.
  • MFA and RBAC for administrative access. Management consoles should require more than a password, and network administrators should reach only the devices they are responsible for rather than holding global configuration rights across the estate.
  • Use secure management protocols only. SSH rather than Telnet, HTTPS rather than HTTP, and SNMPv3 rather than the earlier versions, which carry credentials in the clear.
  • Firmware and patch management. Network device firmware is frequently overlooked compared with servers and endpoints, yet a vulnerability there is severe precisely because of the device's privileged position on the traffic path.
  • Configuration backups under version control, supporting recovery and, just as importantly, detection of unauthorised configuration drift.
  • Segmentation using VLANs and subnetting to separate traffic by function and sensitivity, with micro-segmentation going further to restrict movement between individual workloads even inside a trusted segment.
  • Egress filtering, not only ingress. Unrestricted outbound traffic permits data exfiltration and command and control communication after a compromise, which is how remote access trojans maintain their foothold.
  • Physical port security, disabling unused switch ports and applying MAC address filtering, since physical access to a switch or router bypasses most logical controls entirely.

Device decommissioning and residual data

Study guide: Ch 2 › Data Control › Data Destruction/Disposal; Ch 1 › Emerging Technologies › Internet of Things

Hardening a device covers its working life. Its disposal is a separate problem, because hardware leaving the organisation carries whatever was left on it. This applies to servers and storage, and increasingly to the wide range of connected devices that were never designed with sanitisation in mind.

Example from the field

A well-known UK penetration testing firm has demonstrated this repeatedly by buying second-hand consumer IoT devices from online marketplaces and reverse engineering them. Smart scales acquired this way yielded the previous owners' data in plain text: financial information, health records, home addresses, names, phone numbers, and email addresses. Nothing was encrypted and nothing had been wiped. The lesson generalises well beyond consumer devices, since IoT hardware typically arrives with minimal security out of the box, is rarely updated, and is almost never sanitised before disposal.

Virtual hardware specific configuration

Study guide: Ch 7 › Virtualization Operations; Ch 5 › Managing Virtual Systems

Virtual network devices add complexity beyond the traditional data centre model, because although they perform the same operations as physical devices they have distinct characteristics and configuration surfaces. A specific point worth remembering: storage traffic must be treated as LAN rather than WAN traffic because of its heavy network utilisation and criticality. Latency is the primary concern for storage, unlike general network traffic which is more flexible and resilient to delay.

Configuration also covers memory and CPU allocation, and the distinction between Type 1 hypervisors, which run directly on the hardware, and Type 2 hypervisors, which run as an application on top of a host operating system. Type 1 is standard for production cloud infrastructure because it presents a smaller attack surface, having no underlying host operating system to compromise.

Secure by default

Study guide: Ch 5 › OS Hardening, Monitoring, and Remediation

Systems should ship and deploy in their most secure configuration, with the customer deliberately relaxing settings where needed rather than having to discover and tighten insecure defaults. This inverts the failure mode: an overlooked setting leaves the system secure rather than exposed.

Installation and configuration of management plane tools

Study guide: Ch 5 › Securing the Management Plane

The virtualisation platform dictates which management tools are installed on each host. The most recent versions should be installed, and the procedure for updating them belongs in the configuration management plan. Adequate server resources must be allocated so virtual machines can be migrated during updates to the virtualisation platform, which is what allows maintenance without downtime.

Guest operating system virtualisation toolsets

Study guide: Ch 5 › Managing Virtual Systems

These are software packages installed inside a virtual machine to optimise performance, management, and integration between the guest operating system and the host environment. They improve functionality and manageability, but each toolset is also code running with privilege inside the guest, so it must be kept patched and installed only from trusted sources.

Keeping the environment secure once it is running

Access controls for local and remote access

Study guide: Ch 5 › Securing Communications and Infrastructure › Bastion Hosts

Access controls ensure only authorised individuals reach sensitive resources, combining physical practices with logical controls. Local access control secures physical and console access to systems.

Local access control begins with the physical premises: CCTV, trained security personnel monitoring access points, physical or biometric locks, and smart cards using NFC to restrict entry to authorised staff. On-site authentication should combine factors in the same way remote authentication does, pairing something the person has, such as a card, with something they are, such as a biometric.

Example from the field

A trainer arriving at a managed security service provider's site at 6am was met by a staff member, badged through, and escorted deep into an older part of the building, then left unattended in a room for half an hour. The staff member had mistaken him for a new employee starting that day. He was never asked for identification. Worse, the area he had been left in sat outside the scope of that organisation's ISO 27001 implementation, so none of the strict access controls documented elsewhere applied there. The point is that physical controls achieve nothing without the processes and procedures behind them, and that a certification scope boundary is exactly where those procedures tend to stop.

Remote access mechanisms include RDP and SSH for administrative sessions, secure terminal access, console-based mechanisms, virtual clients, and jumpboxes, also called bastion hosts. The jumpbox pattern is the important one: rather than exposing RDP or SSH directly to the internet on every server, administrators connect to one hardened, tightly monitored intermediary and reach internal systems from there.

Example

A bank places all production servers in private subnets with no inbound internet access. Administrators authenticate to a jumpbox with MFA, and every session through it is logged and recorded. The attack surface drops from every server to one hardened host, and that host is watched closely.

Watch this in the exam

Access control policies define who may reach what, and under what conditions. RBAC assigns permissions by organisational role. ABAC, attribute-based access control, grants access on attributes such as location, device type, or time of access, which makes it the better answer whenever a scenario turns on conditions rather than job title.

Secure network configuration

Study guide: Ch 5 › Securing Communications and Infrastructure (Firewalls, IDS/IPS, Honeypots)

Network security management integrates preventive, detective, corrective, and recovery controls to protect confidentiality, integrity, and availability. The named technologies:

  • VLANs, segmenting a physical network into isolated logical networks.
  • TLS, encrypting data in transit between clients and services.
  • DHCP, automating IP address assignment, which must itself be protected against rogue servers.
  • DNSSEC, adding cryptographic authentication to DNS responses so answers cannot be forged.
  • VPN, providing an encrypted tunnel across untrusted networks.

Network security controls include firewalls, IDS and IPS, honeypots, vulnerability assessments, network security groups, bastion hosts, and segmentation. The distinction between IDS, which detects and alerts, and IPS, which detects and actively blocks, is frequently tested. Honeypots are decoy systems deployed to attract and study attacker activity that has already breached the perimeter.

Operating system hardening

Study guide: Ch 5 › OS Hardening, Monitoring, and Remediation

Hardening reduces an operating system's surface of vulnerability by configuring and strengthening its security settings. Measures include removing unnecessary services and software, closing unused ports, applying least privilege to accounts, and enforcing strong authentication. Hardening is applied through baselines, the defined secure configuration standard, followed by monitoring to detect drift from that baseline and remediation to correct it. The cycle matters more than any single hardening action, because configurations drift continuously.

Patch management

Study guide: Ch 8 › Change and Configuration Management; Ch 5 › OS Hardening, Monitoring, and Remediation

Patch management identifies, acquires, tests, and installs updates to enhance security, improve functionality, and fix defects. Testing before deployment is the step organisations are most tempted to skip and most regret skipping, since an untested patch can cause the outage the patch was meant to prevent. In cloud, patching increasingly means rebuilding from an updated image rather than modifying running instances.

The process runs through identification and assessment, scanning to find missing patches and judging criticality by potential impact, informed by threat intelligence feeds; acquisition and testing, obtaining patches only from trusted sources and proving them in a staging or non-production environment first; and deployment, prioritised by vulnerability severity and system criticality. Tooling such as AWS Systems Manager or Azure Update Management makes this manageable across large, dispersed estates.

Watch this in the exam

Deploy to the most critical systems first, then work outward to less critical ones. Some material states the reverse on the grounds of minimising operational disruption, which inverts the risk logic: the systems that matter most are the ones you least want left exposed while a rollout completes.

Why staging matters

A widely reported 2024 incident saw a security vendor push a faulty content update straight to production endpoints worldwide, causing mass outages across airlines, hospitals, and banks. No attacker was involved. The update itself was the outage, which is precisely the failure mode that testing in a non-production environment exists to catch.

Patching responsibility under IaaS

Study guide: Ch 5 › Foundations of Managed Services › Shared Responsibilities by Service Type

All of which raises a question that comes up constantly in practice: who patches what, when the customer runs its own virtual machines on someone else's hardware. The boundary follows control:

  • Provider: physical hardware and firmware, the hypervisor and virtualisation layer, the physical network fabric, and the underlying storage systems. Hypervisor patching is of particular concern because a flaw there affects every tenant on that hardware.
  • Customer: the guest operating system inside each virtual machine, the middleware, application servers and runtime environments, and the applications themselves.

The provider has deliberately abstracted the layers beneath the boundary and has no visibility into, or responsibility for, what runs inside a customer's instances. That abstraction is the defining characteristic of IaaS, and it is also why the customer cannot defer a hypervisor-level change: the provider controls when infrastructure layer maintenance happens, and the customer has visibility rather than a veto.

Infrastructure as Code

Study guide: Ch 1 › Emerging Technologies › DevOps and DevSecOps

IaC is a DevOps practice managing and provisioning infrastructure through machine-readable definition files rather than physical hardware configuration or interactive tools. It makes infrastructure versioned and reusable, promoting consistency and reducing human error. Its core components:

  • Configuration management tools such as Ansible, Puppet, and Chef, automating configuration files and software installation across servers and maintaining desired state.
  • Orchestration tools such as Kubernetes and Docker Swarm, managing containerised workloads at scale.
  • Provisioning tools such as Terraform and CloudFormation, defining and creating the infrastructure itself.

Beyond consistency, IaC delivers version control, since configurations can be tracked in systems such as Git, rolled back to a previous known-good state, and used as an audit trail of who changed what; automation, giving faster provisioning and updates in environments that scale up and down constantly; and portability across multiple cloud providers and hybrid models.

Because the definition files are code, they can be reviewed, version controlled, and scanned for misconfiguration before anything is deployed, which is what makes IaC a security control rather than merely an efficiency one.

Configuration management tools compared

The three named tools differ in a way the exam can test: how the configuration reaches the managed node.

  • Ansible is agentless and push-based. A control node connects over SSH, applies the state described in a YAML playbook, and disconnects. Nothing is installed on the target. Trade-offVery low barrier to entry, since YAML is readable without a programming background, and no agents to install, patch, or defend. The push model scales less elegantly than pull for very large fleets running into thousands of nodes.
  • Puppet is agent-based and pull-based. An agent on each node checks in periodically with a central Puppet master, compares current state to desired state, and self-corrects drift automatically without anyone triggering it. Trade-offStrong for continuous compliance enforcement and mature reporting, which is genuinely useful for demonstrating evidence to a PCI DSS or HIPAA auditor. Steeper learning curve, and the agent carries its own attack surface and operational overhead.
  • Chef is also agent-based and pull-based, periodically pulling its assigned run list from a central server. Configuration is written in Ruby, making it genuinely procedural code rather than declarative state. Trade-offPowerful and flexible for teams with strong development backgrounds who want full procedural control, and well suited to complex customised logic. It carries the same agent overhead as Puppet.
Watch this in the exam

Push versus pull is the distinguishing axis. Ansible pushes on demand and installs nothing. Puppet and Chef pull on a schedule and self-correct drift continuously. If a scenario requires configurations to stay enforced without human intervention, that points at a pull-based agent model rather than Ansible.

Orchestration tools compared

  • Kubernetes, originally developed at Google and now maintained by the Cloud Native Computing Foundation, is the de facto standard for container orchestration with by far the largest ecosystem. It groups co-located containers into pods, provides stable networking abstractions so a set of pods stays reachable as individual pods are created and destroyed, and separates configuration and sensitive values from container images, which ties directly to secrets management. It is self-healing, restarting failed containers and rescheduling pods away from failed nodes, and it autoscales on load. It also offers granular RBAC for security segmentation. Security cautionA steep learning curve and high operational overhead mean a large share of real-world cloud misconfigurations originate in poorly hardened clusters: exposed dashboards, overly permissive RBAC, and unencrypted cluster data stores.
  • Docker Swarm is Docker's own built-in orchestration, simpler to learn and quicker to set up, and a natural extension for teams already using Docker and Docker Compose. Its ecosystem is much smaller, its access control markedly less granular, and it is generally considered unsuited to very large multi-team production environments. Industry adoption has shifted decisively toward Kubernetes.

Monitoring the IaC estate

Prometheus is the de facto monitoring standard for cloud-native and Kubernetes environments. It is pull-based, periodically scraping metrics from configured targets over HTTP endpoints rather than having targets push data to it. Grafana is the presentation layer: it stores nothing itself, connecting instead to multiple data sources at once, including Prometheus, CloudWatch, Azure Monitor, and SQL databases, and rendering them as dashboards with its own alerting on top. The pairing is common enough to be spoken of as a single stack.

Example

Prometheus answers "what are the numbers", scraping metrics continuously from every container and node. Grafana answers "show me this in a way a human can interpret at a glance", unifying those metrics with log data and cloud provider telemetry into one pane for the analyst on watch.

Availability of clustered hosts and guest operating systems

Study guide: Ch 7 › Virtualization Operations

Clustered hosts are groups of interconnected servers working together to improve performance, load balancing, and failover. The named capabilities are distributed resource scheduling and dynamic optimisation, which move workloads between hosts automatically; storage clusters; maintenance mode, which evacuates a host so it can be serviced without interrupting workloads; and high availability, restarting affected virtual machines elsewhere when a host fails.

Several further considerations shape whether a cluster genuinely delivers availability:

  • Load balancing distributes incoming traffic evenly so no single host becomes a bottleneck. Balancers may be hardware based, software based, or integrated into the provider's own infrastructure.
  • Failover mechanisms switch automatically to standby capacity when a primary fails, and can be configured at the server, application, or network level depending on what must survive.
  • Health monitoring identifies problems before they escalate, commonly using SNMP for device health and application performance monitoring for service responsiveness and user-facing metrics.
  • Redundancy and replication, where the choice between synchronous replication, which is effectively real time, and asynchronous replication, which is delayed, depends on the criticality of the data and the latency the organisation can accept.
  • Patching the cluster, ideally through automated systems that schedule and deploy updates sequentially across cluster members so that capacity is never lost all at once.

The same thinking extends to guest operating systems. VM redundancy runs multiple instances of the same guest across different physical hosts. Host redundancy places those hosts in different geographical regions and separate data centres, protecting against localised failure. Automatic failover detects failure and shifts workloads to standby machines without administrator intervention, and regular snapshots capture guest state at a point in time for rapid restoration.

Example

A cluster with load balancing but no health monitoring will happily keep sending traffic to a host that has begun failing, because the balancer sees it as available. Adding health checks lets the balancer withdraw that host before users notice, which is why the two controls are specified together rather than treated as alternatives.

Monitoring and backup

Study guide: Ch 8 › Monitoring, Capacity, and Maintenance

Performance and capacity monitoring identifies bottlenecks, resource limitations, and performance issues before they reach end users, covering network, compute, storage, and response time. Hardware monitoring tracks disk health, CPU, fan speed, and temperature, which gives early warning of physical failure. Backup and restore functions for both host and guest operating systems are essential for recovering from failures, cyber attacks, and crashes. A backup that has never been restored is an assumption, so restore testing is what proves the capability exists.

The metrics that matter, and what each indicates:

  • CPU usage, the proportion consumed by virtual machines and applications. Sustained high usage may signal a need for more resource or better optimisation, but it may equally indicate a cyber attack such as cryptomining or a denial of service, so it should never be read as a capacity signal alone.
  • Memory utilisation, where exhaustion produces swapping and sharp performance degradation.
  • Network latency and throughput, the time data takes to traverse the network and the volume carried. High latency or unusual traffic volume can indicate network problems or exfiltration.
  • Application response times, which reflect the actual user experience rather than infrastructure health.

Provider-native tooling covers most of this: AWS CloudWatch, Azure Monitor, and Google Cloud Operations Suite. Third-party platforms add cross-cloud visibility, and custom scripts fill gaps neither covers. Whatever the source, the output belongs on centralised dashboards with agreed alert thresholds, so that a breach of a threshold prompts investigation rather than sitting in a log nobody reads.

Capacity management extends monitoring forward in time: analysing historical data for trends, applying auto-scaling policies so resources grow and shrink with demand, using predictive analytics to forecast requirements from usage patterns and business growth projections, reserving capacity for crucial applications ahead of peak periods, establishing performance baselines to measure future readings against, and conducting load testing to see how the infrastructure behaves under varying load before real demand arrives.

Backup types and restore procedures

  • Full backup, a complete copy of all data. The baseline everything else is measured from, and the slowest and largest to take.
  • Incremental backup, only the changes since the last backup of any kind. Smallest storage footprint, but restoration requires the full backup plus every increment since, so recovery is slower.
  • Differential backup, all changes since the last full backup. Larger than incremental but faster to restore, needing only the full backup plus the latest differential.

A common schedule pairs a weekly full backup with daily incrementals. Storage may be network attached or cloud based, and in either case backups should be encrypted, compressed to control cost, and above all verified by testing restoration.

For guest operating systems, snapshot-based backups capture the virtual machine at a point in time, while agent-based backups install software inside the guest to enable file level protection, using tools such as Veeam Agent or Azure Backup. Restore procedure follows the failure type: boot and recovery media plus a system state restore for complete host failure, a snapshot rollback for recent or minor guest issues, and an agent-driven file level restore for partial data loss where rolling the whole machine back would be disproportionate.

Watch this in the exam

Incremental minimises storage and maximises restore time. Differential does the opposite. If a scenario emphasises recovery speed, differential is the better fit; if it emphasises storage or backup window constraints, incremental is. Also remember that backups intended to survive ransomware must be segmented from the production network, since encrypting reachable backups is exactly what modern ransomware campaigns attempt first.

Management plane operations

Study guide: Ch 5 › Securing the Management Plane

The management plane controls and administers cloud resources, providing web-based consoles and dashboards for visual management alongside APIs and command line interfaces for automation. Operationally it covers scheduling, orchestration, and maintenance. Because it holds administrative reach across the environment, it warrants the strongest authentication, tightest privilege restriction, and most thorough logging of any component.

Functionally the management plane is used to add, modify, and delete cloud resources including virtual machines, storage, and networks; to collect and analyse data on resource usage, performance, and security events; and to manage user identities, roles, and permissions so that only authorised users can take elevated actions. That logging and monitoring capability is also what supplies evidence for certification against standards such as ISO/IEC 27001, and what makes policy enforcement demonstrable rather than asserted.

Example

A practical control that is easy to overlook: restrict the number of employees who hold hypervisor or management plane access at all. Comprehensive logging then confirms that those few accounts are using resources appropriately. Reducing the population with that reach does more for the risk than any amount of monitoring applied to a large group of privileged administrators.

5.3 Operational controls and standards Study guide reference: Maps to Chapter 8, Operations Management (ITSM process sections). All twelve processes named in the current exam outline are covered here.

The twelve ITSM processes and the frameworks behind them

The outline names eight frameworks. They are frequently offered together as options, so knowing what each governs matters more than knowing any one in depth.

  • ITIL, the body of best practice for IT service management, and the source of the twelve processes below. In practiceUse it when the question concerns how services are run day to day.
  • ISO/IEC 20000-1, the international standard for IT service management, against which an organisation can be certified. In practiceEffectively the certifiable counterpart to ITIL guidance.
  • COBIT, a framework for the governance and management of enterprise IT, aligning IT activity with business objectives through control objectives. In practiceGovernance rather than operations: it asks whether IT is delivering what the business needs.
  • COSO, an enterprise risk management and internal control framework operating at organisational level, widely referenced in financial control contexts. In practiceBroader than IT, covering the whole control environment.
  • CIS Controls, a prioritised set of technical safeguards ordered by defensive value against common attacks. In practicePractical and technical: what to implement first.
  • NIST, particularly SP 800-53 as a comprehensive catalogue of security and privacy controls, alongside the Cybersecurity Framework and Risk Management Framework. In practiceA control catalogue and risk process rather than a service management model.
  • ISO, principally the ISO/IEC 27000 family for information security management, with 27001 specifying the management system requirements. In practiceThe certifiable information security management system.
  • HIPAA, US legislation governing protected health information, including its Security Rule and Breach Notification Rule. In practiceA legal obligation rather than a voluntary framework, applying only to covered entities and their business associates.

Twelve processes follow, and the exam relies on you distinguishing the ones that sound similar.

  • Change management, controlling how changes are requested, assessed, approved, and implemented so that changes do not cause unintended disruption.
  • Continuity management, ensuring services can continue or recover through disruption, linking operations to BC and DR planning.
  • Information security management, the overarching process aligning security controls with business requirements.
  • Continual service improvement management, systematically identifying and implementing improvements to services and processes over time.
  • Incident management, restoring normal service operation as quickly as possible after an unplanned disruption, minimising business impact. It covers detection and recording through monitoring tools, classification, prioritisation, response, and closure.
  • Problem management, identifying, analysing, and resolving the underlying causes of incidents to prevent recurrence, reduce impact, and improve stability.
  • Release management, planning, designing, building, configuring, and testing hardware and software releases so that features, improvements, and fixes are bundled into manageable releases.
  • Deployment management, moving those releases into the live environment.
  • Configuration management, systematically managing and maintaining the configuration of hardware, software, and other assets to preserve integrity, security, and performance, keeping a consistent and accurate record of configurations.
  • Service level management, negotiating, defining, and managing the performance and quality of services delivered to customers, centred on SLAs as formal agreements between provider and customer.
  • Availability management, optimising the capability of the infrastructure, services, and support organisation to deliver a cost-effective and sustained level of availability meeting business requirements.
  • Capacity management, ensuring infrastructure and services have the right amount of resource for current and future demand, balancing cost against performance.

Incident management in practice

Study guide: Ch 8 › Change and Configuration Management › Problem and Incident Management; Ch 7 › Managing Security Operations › Incident Management

Several of those processes carry enough operational detail to be worth taking individually, starting with the two most often confused. Detection and recording draw on monitoring tooling already in place, SIEM platforms, network monitoring, and intrusion detection and prevention systems, all working to reduce mean time to detection. The human channel matters just as much: end users need frictionless ways to report something suspicious, whether by help desk, email, or hotline. The principle is the one used on public transport, that if you see something, you say something, and it works only if reporting is easy enough that people actually bother.

Events are then categorised and classified by severity, which differs between organisations according to business impact, ranging from minor issues to critical outages. Triage addresses the most critical first. A dedicated incident response team, sometimes called a CSIRT, needs both the skills and the delegated authority to act, and must document every step for the post-incident analysis that follows.

Watch this in the exam

Communication obligations begin during the incident, not after it. Internally that means IT, security, HR, and corporate communications. Externally it may include partners and vendors, because they may themselves be data controllers whose customers are affected. If your organisation is acting as a processor, you must notify the controller without undue delay so that they can decide how to notify data subjects. The processor does not make that call.

Problem management in practice

Study guide: Ch 8 › Change and Configuration Management › Problem and Incident Management

Identification runs in two directions. Proactive identification looks for problems before they cause incidents, analysing trends and patterns across previous incident data, system logs, and performance metrics. Reactive identification responds to recurring incidents, systemic issues, or significant outages already reported. Problems are then categorised by nature, whether hardware failure, software defect, network issue, or misconfiguration, which determines what resource is needed to resolve them, and prioritised by impact and urgency.

Resolution addresses the root cause rather than the symptom, which in practice often means patching, reconfiguration, or updating training and awareness programmes. Temporary workarounds may mitigate impact while a permanent fix is developed. Knowledge management then captures what was learned into a knowledge base, which speeds resolution of similar problems and supplies the documented evidence that standards such as ISO/IEC 27001 require. The principle is blunt: if it is not documented, it did not happen.

Example

A cloud service fails three times in a month. Each time, the on-call team restarts the service and users are back within minutes, which is incident management working correctly. Nobody asks why it keeps failing. Problem management is the discipline that investigates the memory leak causing all three, and its absence is why there will be a fourth.

Root cause analysis techniques

Study guide: Ch 8 › Problem and Incident Management; Ch 8 › IT Service Management and Continual Service Improvement

Two techniques come up repeatedly, and they complement rather than compete with each other.

The five whys follows a single causal chain by asking why repeatedly until the answer stops being a symptom. The fishbone diagram, also called Ishikawa, suits incidents with several contributing causes rather than one linear chain: plausible contributing categories are mapped broadly across headings such as people, process, technology, and policy or governance, and the one or two branches with the strongest evidence are then pursued with the five whys to reach something actionable.

Worked example: five whys

Incident: a publicly accessible cloud storage bucket containing sensitive personal data, reported by a security researcher before any confirmed malicious access. Investigation shows it had been set to public read for over six months.

1. Why was the bucket publicly accessible? A developer changed the access control setting to public read to make debugging easier during a troubleshooting session.

2. Why could a developer change bucket permissions directly in production? Their identity and access management role carried permission to modify bucket policies, even though the role had no ongoing access management responsibility.

3. Why did the developer hold such a broad permission? Roles were assigned from a shared developer policy template that granted full storage access across the environment rather than the specific permissions the task required.

4. Why was a broad shared template used instead of least privilege roles? No cloud infrastructure entitlement management process existed, and no periodic access review was in place to right-size permissions.

5. Why was there no entitlement management or review process? Ownership of identity and access management governance was never formally assigned after the migration to cloud. Access provisioning was handled ad hoc by whoever set up each project, with no defined policy and no scheduled review cycle.

Root cause: a governance gap, specifically unassigned ownership of the IAM lifecycle and the absence of periodic entitlement review, which allowed over-permissioned roles to persist unnoticed. The developer's action was the symptom. Disciplining the developer would leave every other over-permissioned role in place and the same incident free to recur.

Release, deployment, and configuration in detail

Study guide: Ch 8 › Change and Configuration Management › Release and Deployment Management; Roles and Process

Release management begins with planning and scheduling: defining the scope and content of the release, identifying which features, updates, and fixes it carries, and setting timelines and resource requirements. A release calendar coordinates stakeholders and avoids clashing with other business activity. The design and build stage produces the release package, and testing then covers unit, integration, system, and user acceptance testing before anything moves. Training materials and documentation are part of the release, not an afterthought.

Deployment management moves the release into production, and the exam expects familiarity with the common strategies:

  • Phased rollout, releasing to a subset of users or systems first and expanding as confidence grows.
  • Big bang, switching everything at once, which is fastest but concentrates risk into a single moment.
  • Blue-green deployment, running two identical environments and switching traffic to the new one, which makes rollback nearly immediate.

The strategy chosen should follow from the complexity and criticality of the release, supported by a risk assessment that identifies critical dependencies and single points of failure beforehand. Post-deployment validation confirms the release functions as expected, drawing on qualitative user feedback as well as quantitative system metrics.

Configuration management and the Statement of Applicability

Configuration management maintains the integrity, security, and performance of hardware, software, and other assets, and supplies the reliable baseline that system restoration depends on. It also connects directly to ISO/IEC 27001 through the Statement of Applicability, the document recording all 93 Annex A controls alongside justification both for including a control in the information security management system and for excluding one. Being required to justify exclusions is what stops the SoA becoming a list of the controls an organisation already happened to have.

Watch this in the exam

Incident management restores service fast. Problem management finds and eliminates the root cause so it stops happening. A scenario describing urgency and restoration wants incident management; one describing recurrence and underlying cause wants problem management. Equally, release management prepares and tests the release, deployment management puts it into production, and change management authorises it.

Availability and capacity management in detail

Study guide: Ch 8 › Monitoring, Capacity, and Maintenance; IT Service Management and Continual Service Improvement

Availability management optimises the capability of services, infrastructure, and the support organisation to deliver a cost-effective and sustained level of availability that lets the business meet its objectives. Its benefits run beyond uptime: fewer and shorter outages, better customer satisfaction, less time and resource consumed handling incidents, and a return on investment from preventive maintenance that avoids the far higher cost of emergency repair and lost productivity.

Why availability carries a financial number

A major UK vehicle manufacturer disrupted by a cyber attack in 2025 was reported to be losing in the order of tens of millions per week, and several weeks in sought UK government loan support running to over a billion pounds, with commentary suggesting a measurable effect on national output. Whatever the precise figures, the lesson holds: availability is not an IT metric, it is a financial one, and preventive investment is measured against losses of that scale rather than against the cost of the control.

Capacity management divides into three sub-processes, and the distinction is examinable:

  • Business capacity management, translating future business plans and growth projections into future capacity requirements.
  • Service capacity management, managing the performance of the live services themselves against agreed targets.
  • Component capacity management, managing the individual underlying components such as CPU, memory, storage, and bandwidth.

All three depend on information that does not come from monitoring tooling alone. Growth projections and planned initiatives surface through regular management reviews with senior leadership, which is how a security function learns where the organisation is heading and what technologies it intends to adopt before capacity becomes a constraint.

5.4 Digital forensics Study guide reference: Maps to Chapter 8, Operations Management (digital forensics section), with related legal material in Chapter 9.

Collecting, acquiring, and preserving evidence that will hold up

Forensic data collection methodologies

Study guide: Ch 9 › Cloud Forensics › Collection and Acquisition

The central distinction is between live data acquisition, capturing data from a running system including volatile memory, network connections, and running processes, and static or dead acquisition, capturing data from a powered-down system. Live acquisition is necessary because volatile evidence such as memory contents, encryption keys held in RAM, and active network connections disappears the moment power is lost. This is why the standard incident response guidance is to contain while preserving rather than to shut systems down immediately.

Order of volatility governs collection sequence: capture the most transient evidence first, working from CPU registers and cache, through RAM and network state, to disk and finally archived media.

Beyond live and static acquisition, several specialised branches appear in the outline:

  • Network forensics, capturing and analysing traffic and logs to establish what was transmitted, which connections existed, and where a breach reached. Tools include Wireshark, tcpdump, and NetworkMiner.
  • Cloud forensics, acquiring logs, storage data, and user activity records through the provider's own APIs and tooling, since the customer cannot reach the underlying media.
  • Memory forensics, analysing RAM to recover artefacts, open network connections, loaded drivers, and other live system state that exists nowhere else.
  • Mobile device forensics, extracting messages, call logs, application data, and the associated metadata including location information, using specialist tooling such as Cellebrite or Oxygen Forensic Suite.
Watch this in the exam

Cloud acquisition depends on provider APIs and on what the contract permits, which is why forensic readiness in cloud is a procurement question as much as a technical one. If a scenario has an investigator wanting the underlying disk from a managed service, the realistic answer involves the provider and the agreement rather than a tool the customer can run.

Evidence management

Study guide: Ch 9 › Cloud Forensics › Evidence Preservation and Management

Evidence management ensures digital evidence is collected, preserved, and presented so that its integrity and admissibility hold in legal contexts. Chain of custody is the core mechanism, documenting every person who handled the evidence, when, and why, demonstrating it was not tampered with.

Collecting, acquiring, and preserving

Study guide: Ch 9 › Cloud Forensics › Collection and Acquisition; Evidence Preservation and Management

Collection is the initial gathering of evidence from its sources. Acquisition creates the working copy. Preservation protects the integrity of the evidence from collection through analysis to presentation in court, using three named techniques:

  • Imaging, creating a bit-for-bit copy so that analysis is performed on the copy and the original remains untouched.
  • Hashing, computing a cryptographic hash at collection and re-verifying it later to prove the evidence has not changed.
  • Write blockers, hardware or software preventing any write operation to the source media during acquisition.
Example

An investigator images a suspect volume through a write blocker, hashes both original and image, and confirms the values match. Every subsequent analysis runs against the image. If the defence later questions whether evidence was altered, the matching hashes and the custody log answer the question, which is precisely what makes the finding usable.

Handling evidence end to end

Study guide: Ch 9 › Cloud Forensics › Collection and Acquisition; Evidence Preservation and Management

Those three techniques sit inside a wider sequence that the exam expects you to know in order: collection, transport, analysis, storage, and presentation. Collection begins with identification, determining what data is in scope for the investigation, then documentation of each item's location, condition, and the context it was found in, using photographs, video, or written notes as appropriate. The scene must be secured against unauthorised access or tampering, which may mean isolating devices, controlling entry points, and maintaining a log of everyone who enters. Handling uses write blockers, static-free bags, and secure containers so nothing changes state in transit.

Secure storage deserves more attention than it usually gets: access control restricting who can reach the evidence, physical measures such as locked cabinets and controlled-access rooms, environmental control of temperature and humidity to preserve the physical integrity of the media, and redundancy across locations to protect against hardware failure or disaster. Documentation throughout covers case notes, chain of custody records for each transfer, and the forensic analysis report itself, which must be detailed enough that another examiner could reproduce the findings.

Example from practice

An organisation building forensic capability created a dedicated isolated environment for evidence collection, deliberately separated from both the corporate network and the production cloud estate, with a defined and logged procedure for moving data between that environment and the organisation proper. Corporate laptops turn out to matter as much as cloud workloads here: cloud services generate audit logs by default, whereas a compromised physical endpoint may hold the only copy of what happened. Every step of handling was logged, tracked, signed, and formally declared. It is a materially heavier process than routine incident handling, which is exactly why it needs to be designed before it is needed.

Legal compliance frames all of it. Evidence handling must satisfy applicable privacy law such as GDPR, follow recognised standards from bodies such as NIST and ISO, and respect jurisdictional differences in where evidence was collected and analysed. Regular internal audits confirm the procedures are followed in practice rather than merely written, and periodic external review confirms they match current best practice.

Watch this in the exam

Cloud complicates forensics specifically: the customer often cannot seize hardware, may not know its physical location, and shares infrastructure with tenants whose data must not be captured. Forensic capability in cloud therefore depends heavily on the contract and on what the provider will support, which is a recurring theme across this certification.

5.5 Communication with relevant parties Study guide reference: Maps to Chapter 8, Operations Management (communication and stakeholder management sections).

Who needs to know, and what they need

Managing communication means establishing clear, consistent channels so that all relevant parties are informed, aligned, and engaged. Each audience has different needs:

  • Vendors, requiring clear channels covering service performance, contractual obligations, security incidents affecting shared services, and change notification. Communication is a vendor management function as much as an operational one.
  • Customers, requiring timely, accurate information about service status, incidents affecting them, planned maintenance, and any breach touching their data. Contractual and regulatory notification obligations frequently apply.
  • Partners, requiring coordination on shared processes and integrated services, including how incidents are jointly handled.
  • Regulators, requiring communication that demonstrates compliance and maintains good standing. This includes establishing channels before they are needed, meeting mandatory reporting deadlines such as breach notification, and responding to enquiries with accuracy.
  • Other stakeholders, including internal leadership, staff, insurers, and where relevant law enforcement and the public.

Communicating during an incident

Study guide: Ch 10 › Manage Communication with Relevant Parties; Ch 8 › Problem and Incident Management

An incident produces obligations in several directions at once, on different clocks, and the audiences need different detail at different moments. That is why the channels have to exist beforehand rather than being improvised while the investigation is still running.

Example

The GDPR 72-hour notification clock does not pause for weekends. An organisation breached late on a Friday must be in a position by Monday to supply its supervisory authority, the Information Commissioner's Office in the UK, with the information required on the breach notification form. That is an operational staffing question as much as a legal one, and it is the reason on-call arrangements and pre-drafted notification templates exist.

Example

A collaborative incident response team should draw on IT, security, GRC or legal, and public relations, because the incident produces obligations in all four directions at once. Failing to communicate to affected data subjects in a timely fashion can itself attract a penalty, separate from and on top of whatever the breach cost.

Example

A telecom operator confirms a breach affecting customer data. Within the same window it must notify its regulator inside the statutory deadline, inform affected customers, brief its board, coordinate with the SaaS vendor whose platform was involved, and manage press enquiries. Each audience needs different detail at a different time, which is why the channels must exist before the incident rather than being improvised during it.

Subject access requests and the front line

Study guide: Ch 9 › Privacy in the Cloud; Ch 10 › Manage Communication with Relevant Parties

A data subject access request starts a clock the moment it is made, and the organisation generally has one calendar month to respond. The practical difficulty is recognition rather than response, because a data subject is under no obligation to use the correct terminology. Someone asking what information you hold about them, or what address you have on file, has made a valid request whether or not they call it one. That makes front-line training a compliance control in itself, since the clock runs from the moment the question is asked rather than from the moment somebody senior recognises what it was.

Communicating with regulators

Study guide: Ch 9 › U.S. Privacy and Security Laws; International Laws; Ch 10 › Manage Communication with Relevant Parties

The Data Protection Officer, a role established under GDPR, is the conduit between the organisation and the supervisory authority, and the role exists in both controller and processor organisations. Reporting mechanisms have modernised, with the UK regulator now expecting breach reports through its online service rather than a form. Failing to report properly, or lacking an effective channel through a DPO, can attract a penalty in its own right, separate from any penalty for the breach itself and separate again from class action exposure brought by the data subjects.

Communication with regulators is not solely reactive. Periodic compliance reports, readiness assessments, certification against ISO/IEC 27001 or schemes such as Cyber Essentials, and evidence of corrective action taken in response to earlier findings all maintain standing. Where an ISO/IEC 27001 audit raises non-conformities, whether major or minor, those findings and the response to them belong in the documentation.

Why transparency matters

Attackers increasingly apply pressure through the people whose data they hold rather than only through the breached organisation. A 2025 breach of a nursery management application saw criminals contact parents directly to increase pressure for a ransom payment. Whatever an organisation's instinct to say little while it investigates, the affected individuals may already be hearing from the attacker. That is a substantial part of why notification obligations exist, and why the communication plan has to be ready before it is needed rather than drafted during the incident.

5.6 Manage security operations Study guide reference: Maps to Chapter 8, Operations Management (security operations centre, monitoring, and incident response sections). Penetration testing is named in the current exam outline and is included here.

Running the SOC and the assurance activities around it

Security Operations Centre

Study guide: Ch 7 › Managing Security Operations › Security Operations Center (SOC)

A SOC is a centralised unit handling security issues at organisational and technical level, built on three components: people, meaning skilled analysts, incident responders, and managers; process, the defined procedures they follow; and technology, the tooling that gives them visibility and response capability. All three are required, and a common failure is investing in technology while under-resourcing the people and processes needed to use it.

Alert fatigue

A poorly tuned SIEM produces so many alerts that analysts stop distinguishing signal from noise. The problem is not looking for a needle in a haystack; it is looking for a needle in a stack of needles. Tuning to reduce false positives is therefore a security control in its own right, because an alert nobody investigates provides no protection however accurate it was.

The process element means documented playbooks for monitoring, incident response, and threat hunting. Threat hunting is the proactive half: analysts going looking for indicators rather than waiting for an alert, checking for signs such as lateral movement, privilege escalation, or the use of compression tools that typically precede exfiltration. A managed provider may trigger hunting activity in each customer environment on a defined cycle rather than only on suspicion. The technology element covers IDS and IPS, endpoint detection and response, SIEM, and threat intelligence feeds, both commercial and open source such as those published by national cyber security bodies.

Building or buying a SOC

Study guide: Ch 7 › Managing Security Operations › Security Operations Center (SOC); Ch 10 › Cloud Contract Design › Vendor Management

Assembling all three elements is expensive, which is why the model itself is a decision rather than an assumption. Standing up an in-house SOC is a significant capital commitment, with industry estimates for a mature organisation of a thousand people or more running to several million in initial investment before ongoing staffing is counted. That cost, combined with a persistent global shortfall in qualified security staff, is why many organisations use a managed SOC from an MSSP, or a hybrid model pairing an internal team with external coverage outside working hours.

Watch this in the exam

Whichever model is chosen, a shared responsibility model applies between the organisation and the provider, and it must be documented explicitly in the contract and the SLAs. That includes who is responsible for meeting breach notification deadlines, because a monitoring provider detecting an incident does not discharge the customer's own regulatory obligation to report it.

Intelligent monitoring of security controls

Study guide: Ch 7 › Managing Security Operations › Continuous Monitoring

Intelligent monitoring uses advanced technology to continuously oversee and analyse security mechanisms, aiming to detect, prevent, and respond efficiently. By leveraging automation, machine learning, and artificial intelligence, organisations extend their capability beyond what manual review can achieve at cloud scale. The controls monitored include firewalls, IDS and IPS, honeypots, and network security groups. The consistent principle across this certification is that AI augments analysts rather than replacing them, handling volume so humans can concentrate on complex and novel cases.

Those controls fall into four categories, a grouping that maps onto the 93 controls in Annex A of ISO/IEC 27001 and is worth carrying into the exam:

  • Preventative, acting before the fact: firewalls, access control lists, and antivirus or anti-malware preventing execution of malicious software.
  • Detective, identifying and alerting: intrusion detection systems, which are passive and alert only, and SIEM platforms correlating activity across sources.
  • Corrective, acting to contain and remedy: intrusion prevention systems, which sit inline and block, together with patch management and change management addressing the underlying weakness.
  • Recovery, restoring after the fact: backup solutions segmented from the network, and disaster recovery plans that have been stress tested rather than merely written.
Example

Modern endpoint protection illustrates the shift in preventative controls. Rather than matching against a signature list that must be constantly updated, current tooling applies machine learning to assess several hundred characteristics of a file before it executes. That is what allows it to catch a threat with no signature yet written, which signature-based scanning by definition cannot.

How the technique transferred

The approach came from image classification. Train an algorithm on large numbers of labelled images until it reliably separates one category from another, then point the same technique at a different pair of categories: benign files against files carrying a payload. The vendor that commercialised this became one of the fastest companies in the sector to reach a billion dollar valuation before being acquired, which is a fair indicator of how significant the shift away from signature matching proved to be.

Log capture and analysis

Study guide: Ch 3 › Log Capture and Analysis

Log management runs through collection, storage, analysis, and response. SIEM platforms aggregate and correlate logs from across the environment, turning isolated events into detectable patterns. Threat intelligence supplies external context about active threats and indicators of compromise, sharpening what the SIEM is looking for. Log storage must be secure and tamper-resistant, since altering logs is among an attacker's first moves.

The full process runs through collection from applications, network devices, and servers; secure and scalable storage preserving integrity and access control at the volumes cloud generates; analysis to identify patterns and anomalies, increasingly assisted by machine learning; real-time monitoring so indicators of compromise are acted on before they escalate; compliance and auditing, where the log trail is the evidence; and integration with incident response, so that a detection reaches the response team through a defined escalation path rather than sitting in a queue.

Selecting a SIEM

Evaluation criteria worth carrying into practice: quality of automation, breadth of intelligence feeds, and how easily rules can be written and tuned. Platforms range from higher cost enterprise products with mature communities and support through to lighter, more recent offerings with strong real-time detection and AI integration at a lower price point. Analyst comparisons such as Gartner's Magic Quadrant are a reasonable starting point for narrowing the field, and integrated SOAR capability for automated response is increasingly assumed rather than optional.

Evidence and log sources

A question that arises in practice: can logs held in a central platform serve as evidence in court, or must the original be retained from the source? The safer position is to preserve the original wherever possible, captured using appropriate forensic tooling. Aggregated copies may be admissible depending on the matter, but the original source record is what withstands challenge.

Incident response

Study guide: Ch 7 › Managing Security Operations › Incident Management; Ch 8 › Problem and Incident Management

Incident response follows preparation, detection and analysis, containment, eradication, recovery, and post-incident review. The order matters: containment comes before eradication, and evidence preservation runs alongside containment rather than after it, because volatile evidence is lost when systems are shut down or rebuilt. The post-incident review is what feeds improvement back into preparation.

Root cause versus symptoms

Responding to the same incident repeatedly without asking why it keeps happening is a never-ending game of whack-a-mole. The organisation spends steadily on treating symptoms while the underlying cause remains untouched. Root cause analysis in the post-incident review is what converts response spending into a permanent reduction in incidents, which is precisely the boundary between incident management and problem management.

Lessons learned

A useful framing for post-incident review: in security operations there are no failures, only feedback. Teams that treat the review as an exercise in accountability produce guarded, uninformative accounts. Teams that treat it as feedback surface the detail that actually improves the response plan, which is the entire point of running the review.

Vulnerability assessments

Study guide: Ch 5 › Vulnerability Assessment Tools; Assessing Vulnerabilities

Vulnerability assessment proceeds through identification of assets, scanning for vulnerabilities, risk assessment of what was found, and remediation. It is particularly important in cloud, where resources are dynamically scaled and updated, so the asset inventory changes continuously and a scan is only accurate for the moment it ran. Assessment is broad and automated, identifying known weaknesses across the estate.

Why dwell time matters

Advanced persistent threats are defined by stealth and duration rather than by any single technique: gaining access and remaining undetected for a prolonged period. Consider how much an invisible person in your house would learn about you in a week, then a month. That is the reasoning behind behavioural analytics, which flags anomalous patterns such as impossible travel between login locations, unusual access times, or atypical resource access, precisely because such an intruder generates no alert on any single event.

In more detail, the process runs: asset identification, cataloguing virtual machines, applications, data stores, and network assets, since nothing unknown can be protected; scanning, using automated tooling that compares installed software and configurations against databases of known vulnerabilities such as the CVE list; risk assessment, scoring findings on impact and likelihood, commonly on a one to five scale, so that remediation is prioritised by genuine exposure rather than by raw count; remediation, whether patching, reconfiguring, or decommissioning a system that can no longer be secured, as with an operating system past end of support; and verification and reporting, re-scanning to confirm the finding is genuinely closed and documenting the resulting security posture.

Watch this in the exam

Vulnerability assessment is continuous rather than periodic, for the same reason the cloud asset inventory is never static. New vulnerabilities are disclosed constantly, and a zero day carries that name because defenders have had zero days to prepare for it. A scenario describing an annual scan as sufficient is describing a gap.

Penetration testing

Study guide: Not covered in the 3rd Edition. Ch 5 › Vulnerability Assessment Tools is the closest coverage.

Penetration testing goes further than assessment by actively exploiting weaknesses to demonstrate real impact, showing what an attacker could actually achieve rather than what might theoretically be possible. It may be conducted black-box, grey-box, or white-box depending on how much information the tester is given. In cloud, penetration testing carries an additional constraint: the provider's rules of engagement govern what may be tested, since the infrastructure is shared and testing beyond the customer's own scope would affect other tenants.

Watch this in the exam

Vulnerability assessment identifies and catalogues known weaknesses broadly, usually with automated tooling. Penetration testing actively exploits them to prove impact, and is narrower and more manual. A scenario asking what an attacker could actually accomplish wants penetration testing; one asking what weaknesses exist across the estate wants vulnerability assessment.
